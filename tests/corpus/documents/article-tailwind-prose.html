Why we moved our invoices from a PDF library to plain HTML and CSS

MK Maja Kowalski·14 May 2024 Updated

For six years our invoices were drawn line by line with a PDF library. Every new field meant a developer, a pull request and a deploy. Last spring we replaced 4,000 lines of drawing code with one HTML template.

The old generator positioned every string by hand: doc.text(x, y, label), with x and y computed from font metrics we copied out of the font files. Long customer names overflowed into the amount column, and right-to-left addresses came out reversed.

What we wanted

  1. Templates that designers can change without us.
  2. Tables that break across pages and repeat their headers.
  3. The same output on every server, byte for byte.
    • No fonts from the system.
    • No network access while rendering.

The best layout engine we had was the one in every browser. We just had to stop drawing and start describing.

The template

An invoice is a header, two address blocks, a table and a footer. In HTML that is about sixty lines:

<table class="items">
  <thead><tr><th>Item</th><th>Qty</th><th>Price</th></tr></thead>
  <tbody>
    {% for line in invoice.lines %}
    <tr><td>{{ line.name }}</td><td>{{ line.qty }}</td><td>{{ line.price | money }}</td></tr>
    {% endfor %}
  </tbody>
</table>

Page numbers come from CSS counters in the page margins, which the CSS Paged Media module describes.

What surprised us

Hyphenation, of all things. Narrow columns of German product names look ragged without it, and hyphens: auto needs a lang attribute to work. Keyboard shortcuts in our internal docs, like Ctrl + P, now print as they look on screen.
